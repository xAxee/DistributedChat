# Publication Audit

[[00-Start|Powrót do indeksu]]

Stan przeglądu: **25 lipca 2026**.

## Ocena ogólna

Projekt ma czytelny cel techniczny: pokazuje, jak RabbitMQ może przenosić
zdarzenia między dwiema instancjami API, podczas gdy SignalR dostarcza je do
lokalnie podłączonych klientów. Podział backendu jest konsekwentny, rozwiązanie
ma testy jednostkowe i integracyjne, a lokalne uruchomienie jest spięte przez
Docker Compose.

Przed publicznym wydaniem warto jednak usunąć poniższe blokery.

## P0 — przed publikacją

### Naprawić testy frontendu

`npm test` kończy się wynikiem 8/12. Cztery testy nie dostarczają providera
`APP_CONFIG`, którego wymaga teraz `AuthService`. Dotyczy to testu interceptora
JWT oraz trzech testów `ChatRealtimeService`.

To najpewniej regresja konfiguracji testowej po dodaniu runtime config. Testy
powinny rejestrować testową wartość `APP_CONFIG` albo izolować `AuthService`
przez odpowiedni mock.

### Przywrócić zgodność formatowania

`dotnet format --verify-no-changes` nie przechodzi po przeniesieniu plików do
`backend/`. Większość raportu dotyczy końców linii CRLF oraz brakującego
końcowego newline, podczas gdy `.editorconfig` wymaga LF.

`npm run format:check` również nie przechodzi i wskazuje 19 plików. Przed
publikacją warto wykonać formatowanie raz na całym nowym układzie katalogów,
sprawdzić diff i ponownie uruchomić obie kontrole.

### Zaktualizować podatne zależności NuGet

Restore zgłasza ostrzeżenia `NU1903` dla:

- `Microsoft.OpenApi 2.4.1` — zależność przechodnia,
- `System.Security.Cryptography.Xml 10.0.9` — wersja przypięta centralnie.

Przed publikacją należy ustalić bezpieczne wersje, zaktualizować pakiety i
ponownie wykonać `dotnet restore`, `dotnet test` oraz audyt
`dotnet list package --vulnerable --include-transitive`.

### Poprawić komendę testową w GitHub Actions

Workflow uruchamia:

```text
npm test -- --no-watch --no-progress --browsers=ChromeHeadless
```

Projekt używa Vitest, a te argumenty pochodzą z konfiguracji Karma/Angular CLI.
Workflow powinien wywoływać po prostu `npm test`. W przeciwnym razie CI może
zakończyć się błędem niezależnie od samych testów.

## P1 — wysoki priorytet

### Dodać formatowanie frontendu do CI

Skrypt `npm run format:check` istnieje, ale żaden workflow go nie uruchamia.
Warto dodać go do joba frontendu w CI dla pull requestów.

### Sprawdzić budżety bundla

Build frontendu przechodzi, ale zgłasza trzy ostrzeżenia: główny bundle ma około
593 kB przy budżecie 500 kB, a style stron pokoi i czatu przekraczają limit 4 kB.
Można ograniczyć importy i powtarzające się style albo świadomie skorygować
budżety w `angular.json`.

### Ujednolicić kontrolę backendu na `main`

Pull request sprawdza `dotnet format --verify-no-changes`, ale workflow dla
`main` już nie. Najbezpieczniej utrzymywać ten sam podstawowy zestaw kontroli w
obu miejscach albo wydzielić wspólny reusable workflow.

### Przypiąć obrazy i akcje

Tagi obrazów (`postgres:18.1-alpine`, `rabbitmq:4.1-management-alpine`,
`nginx:1.29-alpine`) są wygodne, ale nie gwarantują identycznego obrazu w
przyszłości. Dla bardziej powtarzalnych buildów można przypiąć digesty.
Analogicznie, publiczne repozytorium o wyższym rygorze może przypinać akcje
GitHub do pełnych SHA.

### Dodać pliki społecznościowe repozytorium

Przed publicznym udostępnieniem warto dodać:

- `LICENSE`,
- krótki `CONTRIBUTING.md`, jeśli przyjmowane będą zmiany,
- szablon Dependabot lub Renovate dla NuGet, npm, Docker i GitHub Actions.

## P2 — dalsze usprawnienia

- Outbox dla zdarzeń RabbitMQ, aby zapis wiadomości i publikacja zdarzenia nie
  mogły się trwale rozjechać.
- Distributed rate limiting zamiast limitów osobnych dla każdej instancji.
- Pełniejszy model presence odporny na zerwane połączenia i awarie instancji.
- Refresh tokeny, unieważnianie sesji oraz bardziej rozbudowana autoryzacja.
- Metryki i tracing dla przepływu HTTP → PostgreSQL → RabbitMQ → SignalR.
- Więcej testów frontendu na poziomie komponentów i przynajmniej jeden test E2E
  dla komunikacji między klientami podłączonymi do różnych instancji.

## AI smells

Nie znaleziono w kodzie komentarzy typu „generated by AI”, sztucznych TODO,
placeholderów ani oczywistych, porzuconych atrap.

Widoczne są jednak łagodniejsze symptomy, które często pojawiają się po
generowaniu lub szybkiej rozbudowie projektu:

- dokumentacja była bardzo rozbudowana względem niewielkiego MVP i powtarzała
  te same informacje w README oraz wielu notatkach;
- po reorganizacji katalogów dokumentacja nadal wskazywała stare ścieżki;
- workflow zachował argumenty niepasujące do używanego runnera testów;
- nazwy i opisy w dokumentacji miejscami nie odpowiadały już kodowi.

To nie przesądza o pochodzeniu kodu. Są to przede wszystkim oznaki braku
końcowego, całościowego przeglądu po zmianach. Krótsze README, aktualna baza
wiedzy i działające CI znacznie poprawią odbiór repozytorium.
